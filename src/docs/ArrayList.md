# ArrayList 복습 노트

> 배열과 리스트의 차이를 비교하면서, `ArrayList`가 어떤 문제를 해결하는지 정리했다.  
> 강의 예제 전체를 옮기기보다 자료구조의 특징과 성능 차이를 중심으로 다시 적었다.

---

## 1. 배열에서 인덱스 조회가 빠른 이유

배열은 같은 종류의 데이터를 연속된 공간에 저장한다.  
그래서 인덱스를 알고 있으면 해당 위치를 바로 계산해서 접근할 수 있다.

```java
int value = numbers[2];
```

배열의 시작 위치와 한 요소가 차지하는 크기를 알면 원하는 칸의 위치를 계산할 수 있다.  
이 때문에 인덱스를 이용한 조회와 변경은 데이터 개수와 관계없이 일정한 시간이 걸린다.

```text
인덱스 조회: O(1)
```

내가 이해한 핵심은 다음과 같다.

> 배열은 “몇 번째 칸인지” 알고 있을 때 가장 강하다.

---

## 2. 값으로 검색할 때는 상황이 달라진다

찾고 싶은 값만 알고 인덱스를 모른다면 배열의 앞에서부터 하나씩 비교해야 한다.

```text
for(int number : numbers) {
  if(number == target) {
    break;
  }
}
```

찾는 값이 마지막에 있거나 아예 없다면 전체 요소를 확인해야 한다.

```text
순차 검색: O(n)
```

첫 번째 요소에서 바로 찾는 경우도 있지만, 자료구조의 성능을 비교할 때는 보통 데이터가 많아졌을 때의 증가 추세를 본다.

---

## 3. 빅오 표기법을 보는 기준

빅오 표기법은 입력 데이터가 늘어날 때 연산량이 어떤 비율로 증가하는지 나타낸다.

| 표기 | 의미 | 예시 |
|---|---|---|
| `O(1)` | 데이터 크기와 무관하게 연산량이 거의 일정함 | 배열 인덱스 조회 |
| `O(n)` | 데이터 수에 비례해서 연산량이 증가함 | 배열 전체 검색 |
| `O(n²)` | 데이터 수가 늘수록 연산량이 제곱으로 증가함 | 중첩 반복문 |

중요한 점은 정확한 실행 시간을 계산하는 것이 아니라, 데이터가 커졌을 때 어떤 연산이 더 빠르게 부담이 커지는지 비교하는 것이다.

---

## 4. 배열 중간에 데이터를 넣기 어려운 이유

배열은 요소 사이에 빈칸을 자동으로 만들어 주지 않는다.

예를 들어 다음 배열의 1번 위치에 값을 추가한다고 생각해 보자.

```text
[A, B, C, null]
```

새 값을 넣으려면 뒤쪽 요소부터 한 칸씩 밀어야 한다.

```text
[A, B, C, null]
[A, B, C, C]
[A, B, B, C]
[A, X, B, C]
```

앞쪽 요소부터 옮기면 기존 값을 덮어쓸 수 있으므로, 이동은 뒤에서부터 시작해야 한다.

### 위치에 따른 추가 비용

- 맨 앞에 추가: 거의 모든 요소를 이동해야 하므로 `O(n)`
- 중간에 추가: 뒤쪽 일부를 이동하므로 평균적으로 `O(n)`
- 마지막에 추가: 이동할 요소가 없다면 `O(1)`

삭제도 비슷하다.  
앞이나 중간의 값을 지우면 빈 공간을 채우기 위해 뒤쪽 요소를 앞으로 당겨야 한다.

---

## 5. 배열의 고정 크기 문제

배열은 생성할 때 길이를 먼저 정해야 한다.

```java
String[] participants = new String[100];
```

실제 데이터가 10개만 들어오면 남은 공간은 사용되지 않는다.  
반대로 100개보다 더 많이 들어오면 기존 배열만으로는 저장할 수 없다.

이 부분에서 배열은 두 가지 선택을 요구한다.

- 넉넉하게 만들고 남는 공간을 감수한다.
- 작게 만들고 부족할 때 더 큰 배열을 새로 만든다.

데이터 개수를 미리 알기 어려운 상황에서는 직접 크기를 관리하는 일이 번거롭다.

---

## 6. 배열 리스트가 해결하는 부분

배열 리스트는 내부적으로 배열을 사용하지만, 사용자가 배열 크기를 직접 관리하지 않도록 감싼 자료구조다.

리스트의 공통 특징은 다음과 같다.

- 요소의 순서가 있다.
- 같은 값을 여러 번 저장할 수 있다.
- 필요한 경우 저장 공간을 늘릴 수 있다.

배열과 비교하면 이렇게 정리할 수 있다.

| 구분 | 배열 | 배열 리스트 |
|---|---|---|
| 순서 | 있음 | 있음 |
| 중복 | 허용 | 허용 |
| 크기 | 생성 시 고정 | 필요에 따라 확장 |
| 인덱스 조회 | 빠름 | 빠름 |
| 중간 추가·삭제 | 요소 이동 필요 | 요소 이동 필요 |

배열 리스트가 크기를 자동으로 늘려 주더라도, 내부가 배열이라는 점은 변하지 않는다.  
따라서 앞이나 중간에 데이터를 넣을 때 요소를 이동해야 하는 한계는 그대로 남는다.

---

## 7. ArrayList의 주요 연산 정리

| 연산 | 예상 시간 복잡도 | 이유 |
|---|---:|---|
| 인덱스 조회 | `O(1)` | 원하는 위치를 바로 계산할 수 있음 |
| 값 검색 | `O(n)` | 앞에서부터 비교해야 함 |
| 마지막 추가 | 평균 `O(1)` | 보통 기존 요소 이동이 없음 |
| 앞·중간 추가 | `O(n)` | 뒤 요소를 한 칸씩 이동해야 함 |
| 마지막 삭제 | `O(1)` | 마지막 요소만 제거하면 됨 |
| 앞·중간 삭제 | `O(n)` | 빈 공간을 채우기 위해 요소를 이동해야 함 |

마지막 추가는 내부 배열이 가득 찬 순간에는 더 큰 배열로 복사하는 비용이 생길 수 있다.  
하지만 평소에는 마지막 칸에 값을 넣는 방식이므로 평균적으로 빠르게 동작한다고 이해했다.

---

## 8. 내가 정리한 사용 기준

`ArrayList`는 다음 상황에 잘 맞는다.

- 인덱스로 자주 조회한다.
- 데이터를 주로 뒤에 추가한다.
- 순서와 중복이 필요하다.
- 중간 삽입·삭제보다 조회가 더 중요하다.

반대로 앞이나 중간에서 추가·삭제가 매우 자주 발생한다면, 배열 기반 구조의 이동 비용을 고려해야 한다.

---

## 핵심 정리

- 배열은 인덱스를 알고 있을 때 `O(1)`로 접근할 수 있다.
- 값을 직접 찾는 검색은 보통 `O(n)`이 필요하다.
- 배열 중간에 값을 추가하거나 삭제하면 요소 이동이 발생한다.
- 배열은 크기가 고정되어 있어 데이터 수를 예측하기 어려울 때 불편하다.
- 배열 리스트는 크기 관리를 대신해 주지만, 내부 배열의 특성까지 없애지는 않는다.
- `ArrayList`는 조회와 마지막 추가가 많은 상황에 적합하다.
