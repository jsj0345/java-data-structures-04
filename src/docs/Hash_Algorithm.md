# 해시 알고리즘 복습 노트

> 배열 인덱스의 빠른 접근을 검색에도 활용하려면 어떻게 해야 하는지 정리했다.  
> 값에서 해시 인덱스를 만드는 과정과 충돌이 발생했을 때의 한계를 중심으로 작성했다.

---

## 1. List와 Set을 비교하며 시작하기

`List`는 순서가 있고 같은 값을 여러 번 저장할 수 있다.

```text
[A, B, A]
```

반면 `Set`은 같은 값을 중복해서 보관하지 않는다.

```text
[A, B]
```

Set에서는 특정 값이 이미 들어 있는지 확인하는 일이 중요하다.  
단순히 모든 요소를 순서대로 비교하면 데이터가 많아질수록 검색 비용이 커진다.

해시는 이 검색 과정을 빠르게 만들기 위해 값과 배열 인덱스를 연결하는 방법이다.

---

## 2. 값을 그대로 인덱스로 사용해 보기

숫자 값과 배열 인덱스를 같게 맞추면 검색이 매우 단순해진다.

```text
Integer[] values = new Integer[10];
values[2] = 2;
values[5] = 5;
```

숫자 `5`가 있는지 확인할 때는 `values[5]`를 보면 된다.

```text
검색: O(1)
```

하지만 값의 범위가 크면 문제가 생긴다.

예를 들어 가장 큰 값이 `9999`라면 몇 개의 값만 저장하더라도 매우 큰 배열이 필요하다.  
빠른 검색을 얻는 대신 대부분의 공간을 비워 두게 된다.

---

## 3. 나머지 연산으로 인덱스 범위를 줄이기

값을 배열 크기로 나눈 나머지를 인덱스로 사용하면 결과가 배열 범위를 벗어나지 않는다.

```java
int hashIndex(int value, int capacity) {
    return value % capacity;
}
```

배열 크기가 10이라면 결과는 항상 0부터 9 사이가 된다.

```text
14 % 10 = 4
99 % 10 = 9
```

원래 값을 배열에서 사용할 수 있는 범위로 바꾼 결과를 여기서는 해시 인덱스라고 이해했다.

이 방식은 값의 범위와 배열 크기를 분리할 수 있다는 장점이 있다.

---

## 4. 해시 충돌

서로 다른 값이 같은 인덱스로 계산될 수 있다.

```text
9 % 10  = 9
99 % 10 = 9
```

이처럼 다른 값이 같은 해시 인덱스를 얻는 상황을 해시 충돌이라고 한다.

배열 한 칸에 값 하나만 저장하면 나중에 들어온 값이 이전 값을 덮어쓴다.  
따라서 같은 인덱스에 여러 값을 보관할 방법이 필요하다.

---

## 5. 버킷에 여러 값을 저장하기

배열의 각 칸에 값 하나가 아니라 리스트를 두면 충돌한 값을 함께 보관할 수 있다.

```java
LinkedList<Integer>[] buckets = new LinkedList[capacity];
```

구조는 다음처럼 볼 수 있다.

```text
0 → []
1 → [1]
2 → [2]
...
9 → [99, 9]
```

추가 과정은 다음과 같다.

1. 값으로 해시 인덱스를 계산한다.
2. 해당 인덱스의 버킷을 찾는다.
3. 버킷 안에 같은 값이 있는지 확인한다.
4. 중복이 없다면 추가한다.

```text
int index = hashIndex(value, capacity);
LinkedList<Integer> bucket = buckets[index];

if (!bucket.contains(value)) {
    bucket.add(value);
}
```

---

## 6. 해시 검색이 빠른 이유와 한계

해시 인덱스를 계산해서 버킷을 찾는 과정은 빠르다.

```text
배열 인덱스 접근: O(1)
```

하지만 버킷 안에 값이 여러 개 들어 있다면 그 안에서는 다시 비교가 필요하다.

```text
전체 해시 검색
= 인덱스 계산
+ 해당 버킷 내부 검색
```

충돌이 적고 값이 여러 버킷에 고르게 분산된다면 한 버킷에서 확인할 데이터가 적다.  
그래서 추가, 검색, 삭제를 평균적으로 빠르게 처리할 수 있다.

반대로 많은 값이 같은 인덱스에 몰리면 한 버킷을 길게 탐색해야 하므로 성능이 나빠진다.

---

## 7. 배열 크기만 크게 만들면 해결될까

배열 크기를 늘리면 충돌 가능성을 줄일 수 있다.  
하지만 너무 크게 잡으면 사용하지 않는 공간이 많아진다.

따라서 해시 자료구조에서는 두 가지를 함께 고려해야 한다.

- 충돌이 지나치게 많지 않은가
- 배열 공간을 과도하게 사용하지 않는가

단순히 배열을 크게 만드는 것만으로는 좋은 해시 구조가 되지 않는다.

---

## 8. LinkedList가 버킷으로 사용되는 이유

같은 해시 인덱스를 가진 값의 개수는 미리 알기 어렵다.

연결 리스트를 버킷으로 사용하면 필요한 만큼 요소를 추가할 수 있다.

```text
bucket[9] → 99 → 9
```

검색할 때는 9번 버킷까지 바로 이동한 뒤, 그 버킷 안에서 원하는 값을 비교한다.

여기서 중요한 점은 해시가 충돌을 없애는 기술은 아니라는 것이다.

> 충돌 가능성을 받아들이고, 같은 인덱스 안에서 값을 구분할 수 있도록 처리하는 방식이다.

---

## 9. 내가 정리한 해시 처리 흐름

```text
원본 값
  ↓
해시 계산
  ↓
해시 인덱스
  ↓
해당 버킷 접근
  ↓
버킷 안에서 실제 값 비교
```

해시 인덱스는 값을 저장할 후보 위치를 빠르게 찾는 역할을 한다.  
최종적으로 같은 값인지 판단하려면 버킷 내부 비교가 필요하다.

---

## 핵심 정리

- 배열 인덱스 조회는 `O(1)`이지만 값 검색은 보통 `O(n)`이다.
- 값을 인덱스로 바꾸면 검색에 배열의 장점을 활용할 수 있다.
- 나머지 연산을 이용하면 인덱스를 배열 범위 안으로 제한할 수 있다.
- 서로 다른 값이 같은 인덱스를 얻는 상황을 해시 충돌이라고 한다.
- 충돌한 값은 같은 버킷에 함께 보관할 수 있다.
- 해시 연산은 평균적으로 빠르지만, 충돌이 많으면 버킷 검색 비용이 커진다.
- 좋은 해시 구조는 메모리 사용과 충돌 가능성을 함께 고려해야 한다.
